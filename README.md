# maktaba

[English](README.en.md)

**قرص مليء بمشاريع منسيّة يدخل — فهرس يعرف أيّها يعمل اليوم يخرج.**

خادم Node محلي يمسح الأقراص ويبني فهرساً للمشاريع. كل 6 ساعات يشغّل كل مشروع فعلياً، ثم يسجّل هل عمل أم لا. الحكم مقيس، لا مخمَّن.

يفهرس الآن 164 مشروعاً على جهاز واحد: 132 أصلاً و32 نسخة احتياطية. الكود 26,180 سطر JavaScript في 77 ملفاً، مع 19 ملف اختبار وحدة و95 التزاماً في Git.

---

## المشكلة

بعد سنوات من العمل تتراكم المشاريع. المجلد الواحد له ثلاث نسخ، ولا أحد يعرف أيّها الأصل.

ثلاثة أسئلة لا يجيب عنها أي مستكشف ملفات: هل هذا المشروع ما زال يعمل؟ أي منفذ يحجز؟ ما الذي يشغّل نفسه عند الإقلاع؟

الفهرسة سهلة. الصعب أن تعرف الحقيقة بدل أن تخمّنها.

## كيف يشتغل

| الخطوة | الوظيفة |
|---|---|
| 1. المسح | يجوب الأقراص بعمق 6 مستويات، ويتجاهل `node_modules` وأدلة الحزم |
| 2. التمييز | يبصم كل مشروع بـ SHA1 لملف `package.json`، فيجمع النسخ ويختار الأصل |
| 3. الملف التعريفي | يقرأ نقطة البدء والمنافذ والتبعيات وحجم الكود — قراءة فقط، بلا تشغيل |
| 4. فحص الطبيب | يشغّل كل مشروع حتى 20 ثانية، ويحكم من مخرجاته الحقيقية |
| 5. سجل الإقلاع | يقرأ المهام المجدولة ومفاتيح `Run` ومجلدات Startup، ويربطها بأصحابها |
| 6. الإصلاح | عند الطلب، يرسل وكيلاً يصلّح المشروع المكسور — بعد أخذ نقطة رجوع |

الوحدات 43 ملفاً في `lib/`، مجموعها 12,229 سطراً.

## أهم قرار في التصميم

### 1. لا كتابة بلا نقطة رجوع

الوكيل يحصل على صلاحية كتابة كاملة داخل مجلد المشروع. هذا خطر حقيقي على عمل غير محفوظ.

القرار: كل مسار يكتب في مشروع المستخدم يمرّ عبر دالة واحدة، وهي تأخذ نقطة رجوع أولاً.

| حالة المشروع | نقطة الرجوع |
|---|---|
| مستودع Git نظيف | تسجيل `HEAD` — الرجوع بـ `git reset --hard` |
| مستودع Git متّسخ | `git stash -u` وتسجيل مرجع المخبأ |
| ليس مستودعاً | أرشيف zip في `backups/` |
| تعذّر كل ما سبق | **رفض التشغيل** |

التكلفة: بعض الإصلاحات تُرفض. العائد: صفر تعديل بلا طريق رجوع.

الأرشيف ليس حالة نادرة: 96 مشروعاً من 164 في الفهرس بلا مجلد `.git` إطلاقاً.

### 2. حالة «لا أعرف» رمز خروج مستقل

الفاحص يعيد أربعة رموز: 0 سليم، 1 مكسور، 2 خطأ استدعاء، 3 **غير معروف**.

الرمز 3 هو جوهر التصميم. قبله كانت المهلة تعيد 0، فالمشروع المعلَّق يُقرأ سليماً. وفشل الإطلاق كان يعيد 1، فمشروع سليم يُوسم مكسوراً — ثم يصير هدفاً لوكيل يعيد كتابته.

وكان اختبار النجاح تعبيراً نمطياً يبحث عن رقم منفذ. أثر انهيار Node يبدأ بسطر مثل `loader:1459`، وهو رقم من أربع خانات. فالمشروع المنهار كان يُعلَن سليماً باستناداً إلى أثر انهياره.

التوزيع اليوم: 80 سليماً، 30 غير معروف، 54 لم يُفحص بعد. الخانة الثالثة تقول الحقيقة بدل أن تختلق حكماً.

### 3. مؤشر الفحص على القرص

الدورة تستغرق ساعات، وسجل الحارس يُظهر 37 إعادة تشغيل للخادم. كل إعادة تشغيل كانت تعيد الفحص إلى الصفر.

الحل: ملف مؤشر يحفظ ما فُحص. ومعه عدّاد مهلات: مشروع يتعلّق مرتين متتاليتين يُتخطّى. سبب القاعدة أن ستّ دورات متتالية ماتت على المشروع نفسه.

## التشغيل

```bash
npm install
cp config.example.json config.json   # اختياري — يعمل بالإعدادات الافتراضية بدونه
npm start          # الواجهة على المنفذ 4500
npm run truth      # فحص ذاتي، للقراءة فقط، يخرج بقيمة غير صفرية عند الفشل
npm run audit      # تدقيق الأسطول كله
```
