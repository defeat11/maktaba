# maktaba

[English](README.en.md)

**تدخّل قرص فيه مشاريع منسيّة — ويطلع لك فهرس يعرف أيّها شغّال اليوم.**

خادم Node محلي يمسح الأقراص ويبني فهرس مشاريع. كل 6 ساعات يشغّل كل مشروع فعلياً ويسجّل: اشتغل ولا لا. الحكم مبني على قياس، مو على تخمين.

الآن يفهرس 164 مشروعاً على جهاز واحد: 132 أصل و32 نسخة احتياطية. الكود 26,180 سطر JavaScript في 77 ملفاً، ومعه 19 ملف unit test و95 commit في Git.

---

## المشكلة

بعد سنين شغل تتكدّس المشاريع. المجلد الواحد يصير له ثلاث نسخ، وما أحد يعرف أيّها الأصل.

ثلاثة أسئلة ما يجاوب عليها أي file explorer: المشروع هذا لسه شغّال؟ أي port حاجزه؟ وش اللي يشتغل لحاله مع تشغيل الجهاز؟

الفهرسة سهلة. الصعب إنك تعرف الحقيقة بدل ما تخمّنها.

## كيف يشتغل

| الخطوة | الوظيفة |
|---|---|
| 1. المسح | يمشي على الأقراص لعمق 6 مستويات، ويتجاهل `node_modules` ومجلدات الحزم |
| 2. التمييز | يأخذ SHA1 لملف `package.json` كبصمة لكل مشروع، فيجمّع النسخ المكررة ويختار الأصل |
| 3. الملف التعريفي | يقرأ entry point و ports و dependencies وحجم الكود — قراءة فقط، بدون تشغيل |
| 4. فحص الطبيب | يشغّل كل مشروع لين 20 ثانية، ويحكم عليه من مخرجاته الحقيقية |
| 5. سجل الإقلاع | يقرأ المهام المجدولة ومفاتيح `Run` ومجلدات Startup، ويربط كل واحد بمشروعه |
| 6. الإصلاح | لو طلبت، يرسل agent يصلّح المشروع المكسور — بعد ما يأخذ نقطة رجوع |

الكود مقسّم على 43 ملفاً في `lib/`، مجموعها 12,229 سطراً.

## أهم قرار في التصميم

### 1. لا كتابة بلا نقطة رجوع

الـ agent يأخذ صلاحية كتابة كاملة داخل مجلد المشروع. هذا خطر حقيقي على أي شغل ما انحفظ.

القرار: أي كتابة في مشروع المستخدم تمر من دالة وحدة، وهي تأخذ نقطة رجوع أول شي.

| حالة المشروع | نقطة الرجوع |
|---|---|
| Git repo نظيف | يسجّل `HEAD` — والرجوع بـ `git reset --hard` |
| Git repo فيه تعديلات | `git stash -u` ويسجّل مرجع الـ stash |
| مو repo أصلاً | نسخة zip في `backups/` |
| ما نفع ولا واحد منها | **يرفض يشتغل** |

الثمن: بعض الإصلاحات ترفض. المقابل: صفر تعديل بدون طريق رجوع.

النسخة الاحتياطية مو حالة نادرة: 96 مشروعاً من 164 في الفهرس ما عندها مجلد `.git` أصلاً.

### 2. حالة «لا أعرف» رمز خروج مستقل

الفاحص يرجّع أربعة exit codes: 0 سليم، 1 مكسور، 2 خطأ استدعاء، 3 **غير معروف**.

الرمز 3 هو صلب الفكرة. قبله كان الـ timeout يرجّع 0، فالمشروع المعلّق يطلع سليم. وفشل التشغيل كان يرجّع 1، فمشروع سليم ينحسب مكسور — وبعدها يجيه agent يعيد كتابته.

اختبار النجاح كان regex يدوّر على رقم port. أثر انهيار Node يبدأ بسطر مثل `loader:1459`، وهذا رقم من أربع خانات. يعني المشروع المنهار كان يطلع سليم بسبب أثر انهياره نفسه.

التوزيع اليوم: 80 سليم، 30 غير معروف، 54 ما انفحصت لسه. الخانة الثالثة تقول الحقيقة بدل ما تخترع حكم.

### 3. مؤشر الفحص على القرص

الدورة تاخذ ساعات، وسجل الحارس يبيّن 37 إعادة تشغيل للخادم. كل مرة يرجع الفحص من الصفر.

الحل: ملف مؤشر يحفظ وش انفحص. ومعه عدّاد timeouts: المشروع اللي يتعلّق مرتين ورا بعض يتم تخطّيه. سبب القاعدة إن ستّ دورات ورا بعض ماتت على نفس المشروع.

## التشغيل

```bash
npm install
cp config.example.json config.json   # اختياري — يعمل بالإعدادات الافتراضية بدونه
npm start          # الواجهة على المنفذ 4500
npm run truth      # فحص ذاتي، للقراءة فقط، يخرج بقيمة غير صفرية عند الفشل
npm run audit      # تدقيق الأسطول كله
```
